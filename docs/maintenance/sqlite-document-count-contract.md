# SQLite 文档码点计数与索引峰值内存

Refs #444, #463, #476。基底 v1.0.11 / 63e255fab5cb9d817af30b631c3643ccce8e9231，内核 0.2.2-rc.1。

SQLite 会话搜索在首次索引或更新 live / persisted 文档时，用 `Array.from(text).length` 计算排序所需的 Unicode 码点长度。该表达式为整篇文档建立字符数组，而索引只使用数组长度。补丁用 UTF-16 扫描计算相同结果：从 code unit 长度开始，每发现相邻合法高、低代理项减一，并跳过已配对低代理项。孤立代理项仍计一；组合附加符和 ZWJ 仍按码点计数，不改为 grapheme。现有文本清理、SQL 参数、排序、分页、取消与持久化接口保持原语义。

真实公共 Context、SessionStore、SqliteSessionQueryEngine 测试覆盖 live 与冷 JSONL 两条索引路径，包含 ASCII、中英、emoji、组合字符、孤立代理项和保留字符清理；以原码点计数为独立排序 golden，逐页确认无重复或缺失。全文数组调用计数只是分配诊断，不能单独证明用户可感知性能收益。

测量以原 57 补丁再叠已交 665、688 为对照，避免混入其已有优化。独立新进程 4 MiB 混合文档首次真实 search 的 AB/BA 峰值 RSS：对照 201132 / 201072 KiB，候选 162892 / 163032 KiB；查询前峰值75260—75880 KiB，查询增量对照 125872 / 125512 KiB，候选 87252 / 87152 KiB；整个进程峰值减少约 37 MiB。这是该 Linux x64 / Node v24.22.1 进程的峰值结果，不等于 JS 堆峰值，也不是手机内存承诺。

总 search 延迟存在波动。最终冻结源码每种输入每进程一轮预热、三轮采样，AB/BA 合并六样本的中位数：256 B 2.332→2.407 ms，ASCII 64 KiB 5.304→3.956 ms，emoji 64 KiB 6.065→5.397 ms，混合 1 MiB 58.372→52.801 ms，混合 4 MiB 236.680→219.379 ms。此前相同 UTF-16 算法原型的独立 AB/BA 中，4 MiB 为 218.478→231.252 ms，出现退步。因此本项只主张减少全文字符数组及该场景的峰值 RSS，不主张稳定或普遍加速；完整正负测量都保留。早期 for-of 原型未采用，其负面对照另存证据。

会改 runtimeVersion；升级将替换用户运行时。Android 未编译；未跑全量 Flutter、App JVM、PRoot、ARM、真实模型或手机验收。真机验证：在升级前后相同手机导入或保留大文本会话，首次搜索相同词，核结果、排序、继续分页及停止搜索；采集进程内存与总耗时，以真机结果判断收益与时延取舍。没有新增依赖或构建配置修改。
